## 1. 전체 학습 방향

이번 학습은 `공부 → 프로젝트` 순서만 고집하지 않는다.
프로젝트 기능을 만들다가 필요한 개념을 학습하고, 학습한 내용을 다시 프로젝트에 적용하는 방식으로 진행한다.

```text
문제 발견 → 필요한 자료구조 확인 → 개념 학습 → C로 직접 구현 → 프로젝트에 적용 → 테스트 → 문서화
```

이번 로드맵의 핵심은 다음 3가지다.

1. 자료구조를 단순 암기하지 않는다.
2. C 코드로 직접 구현한다.
3. 프로젝트 기능과 연결해서 설명할 수 있게 만든다.

## 3. CSV에 대한 정리

CSV는 이미지 파일이 아니다.
CSV는 `Comma-Separated Values`의 약자로, 데이터를 쉼표로 구분해서 저장하는 **텍스트 파일 형식**이다.

예시:

```csv
id,title,priority,due_date,status
1,C 포인터 복습,5,2026-08-10,TODO
2,스택 구현,4,2026-08-14,TODO
```

이번 프로젝트에서는 처음부터 MySQL이나 Oracle을 붙이지 않고 CSV로 시작한다. 이유는 다음과 같다.

- 설정이 간단하다.
- C 파일 입출력 연습에 좋다.
- 자료구조 구현에 더 많은 시간을 쓸 수 있다.
- 나중에 시간이 남으면 SQLite로 확장할 수 있다.

- 순환 의존성을 감지한다.
- 위상 정렬로 가능한 작업 순서를 계산한다.

### 학습 방식

3. 인접 리스트 방식으로 그래프를 구현한다.
4. DFS로 cycle detection을 구현한다.
5. Kahn 알고리즘으로 topological sort를 구현한다.

### 프로젝트 적용

- `A 작업 완료 후 B 작업 가능` 관계 표현
- 잘못된 순환 관계 차단
- 공부/개발 작업의 가능한 진행 순서 계산

### 산출물

- `docs/01_learning/graph-topological-sort.md`
- `src/graph.c`
- `include/graph.h`
- 순환 의존성 테스트 케이스
- 위상 정렬 실행 결과

### 검증 방법

- `A -> B -> C` 순서가 정상 출력되어야 한다.
- `A -> B`, `A -> C`, `B -> D`, `C -> D` 구조가 정상 처리되어야 한다.
- `A -> B -> C -> A`는 순환으로 감지되어야 한다.
- 자기 자신을 선행 작업으로 등록하면 오류 처리되어야 한다.

## 8. 로컬 커뮤니티 앱 연계 추가 학습

### 8.1 적용 원칙

- 기존 7.1~7.8은 자료구조 자체를 익히기 위한 원래 학습 순서로 유지한다. 이전 예제와 Task Scheduler 적용 예시는 학습 예제로 보존한다.
- 이 절은 현재 로컬 커뮤니티 시뮬레이터에 필요한 내용을 **추가**로 연결한다. 실제 개발 일정과 구현 우선순위는 WBS가 관리한다.
- 화면을 먼저 만드는 대신, C 코어 API와 자료구조를 먼저 완성한 뒤 raylib 화면은 그 API만 호출한다.

### 8.2 도메인 모델과 동적 배열

- `Member`, `Post`, `Comment`, `Reaction` 구조체와 각 ID·작성자 ID·상태값의 책임을 구분한다.
- 각 엔터티 목록은 직접 만든 동적 배열 ADT로 보관하고 `init`, `append`, `find_by_id`, `remove`, `free`의 소유권과 실패 처리를 학습한다.
- 회원가입의 아이디 중복 검사, 로그인 ID 탐색, 글 제목 부분 검색은 우선 선형 탐색으로 구현하고 O(n)인 이유를 기록한다.

### 8.3 댓글 계층과 삭제 규칙

- `parent_comment_id`가 없는 댓글을 루트 댓글, 루트 댓글을 부모로 갖는 댓글만 대댓글로 정의해 깊이를 한 단계로 제한한다.
- 댓글 목록을 순회해 루트 댓글 뒤에 그 자식 댓글을 출력하는 방식을 구현한다. 이는 일반 그래프나 재귀 트리 구현과 구분한다.
- 대댓글이 남아 있는 부모 댓글 삭제는 본문을 `삭제된 댓글입니다`로 바꾸고, 대댓글이 없으면 실제 목록에서 제거한다. 글 삭제는 관련 댓글·반응·향후 투표 데이터를 함께 제거하는 연쇄 삭제 규칙을 별도 테스트한다.

### 8.4 상태 전이, 검색, 정렬

- `ReactionStatus`를 `NONE`, `LIKE`, `DISLIKE`로 두고, 최초 반응은 LIKE 또는 DISLIKE, 이후에는 LIKE와 DISLIKE 사이의 변경만 허용한다. NONE으로 취소하는 전이는 허용하지 않는다.
- 글마다 사용자당 반응 하나만 유지하고, 상태를 변경할 때 집계가 일관되게 갱신되는지 확인한다.
- 제목 부분 검색, 최신순 정렬, 반응 수 기준 정렬을 비교 함수와 함께 구현하고 빈 검색어·결과 없음·동률의 기준을 문서화한다.

### 8.5 다중 CSV 저장·불러오기

- `members.csv`, `posts.csv`, `comments.csv`, `reactions.csv`를 분리하고, 저장 필드 순서와 ID 참조 규칙을 설계한다.
- 한 줄 텍스트만 저장하며 줄바꿈과 CSV 구분 문자는 입력 단계에서 금지한다. 필드별 최대 길이도 상수로 정한다.
- 불러올 때 회원 → 글 → 댓글 → 반응 순으로 읽고, 존재하지 않는 작성자·글·부모 댓글을 참조하는 잘못된 행은 실패 처리한다.

### 8.6 raylib UI 연계 학습 — 8/30 MVP 필수

- C 코어와 CSV 기능이 동작한 뒤 raylib의 창 생성, 입력 처리, 텍스트·버튼·스크롤 가능한 목록, 화면 상태 전환을 학습한다.
- 최소 화면은 로그인, 회원가입, 글 목록·제목 검색, 글 상세, 글 작성·수정, 댓글·대댓글·반응, 프로필 수정·탈퇴, 로그아웃으로 구성한다.
- UI는 저장 파일이나 목록 메모리를 직접 수정하지 않고 C 코어 API의 반환 코드와 결과만 사용한다. 오류는 화면 메시지로 바꿔 표시한다.
- 화면 흐름을 따라 로그인부터 글 작성, 댓글·반응, 로그아웃까지 시연하고 캡처·수동 시나리오를 남긴다.

### 8.7 2차 확장으로 미루는 학습

- 투표는 `Poll`, `PollOption`, `Ballot` 모델과 변경 규칙을 별도 설계한 뒤 추가한다.
- 스택·큐·일반 그래프·힙은 독립 ADT 학습을 유지하고, 커뮤니티 MVP에는 억지로 넣지 않는다.
- Unity Engine 연동은 raylib MVP 완료 후 C 코어를 DLL API로 분리하고 C# UI에서 호출하는 별도 확장으로 진행한다. Unity Test Framework도 이 단계에서 검토한다.
